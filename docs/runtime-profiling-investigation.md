# Runtime profiling investigation

Date: 2026-11-01 (local). Initial diagnosis plus an approved, narrowly scoped
history-prefix optimization follow-up.

The larger synthetic workflows ran roughly twice as fast with the release
native build. Traces identify repeated durable-history work and one-shot host
startup as important investigation areas; evaluating constant-result JavaScript
and crossing the native JSON boundary were comparatively small. This is not a
measurement of the deleted manual lab or a promise of production latency.

The subsequent **release-to-release** comparison supports a narrower result:
the cursor removes substantial replay work, with roughly 5–13% lower median
wall time for the larger synthetic cases in this sample. Small-case timings
are mixed, and cold storage remains slower in a focused repeat. This is a
tested optimization candidate, not a universal speedup or a performance
regression clearance.

A third pass now measures repeated runs through the **existing activated
runtime**. Its reusable host pool makes a substantial difference: candidate
repeated-run medians are 290 ms for two steps, 683 ms for the storage case, and
2313 ms for 32 steps, versus 1086, 1662, and 3493 ms through same-store one-shot
calls. These are local source-embedding measurements, not production SLAs;
activation, the first request, and later requests are reported separately below.

## Question and scope

Why did the earlier manual regression lab take roughly a minute per scenario,
despite its scripts doing very little work?

That lab was deleted, so this investigation does **not** reproduce its exact
workflow or claim to explain every second of its recorded time. Instead, it
establishes new, reproducible measurements against the merged source, using
deterministic synthetic workflows and two native build profiles.

The initial profiling pass changed no runtime behavior. The subsequent approved
cursor implementation is documented below. It changes no storage/authorization
contract, timeout default, dependency, historical baseline, or performance
budget. The globally installed npm CLI and repository's staged addon are not
replaced.

## Measurement boundaries

The investigation uses the current TypeScript compiler and source script host
with the real native durable executor. The combined case uses the existing
lock-capable outcome entrypoint and must succeed without waiting; the ordinary
entrypoint intentionally rejects lock workflows. Other cases use the ordinary
durable entrypoint. Every debug/release pair uses the same entrypoint and inputs.

An embedding-level script deadline of 30 seconds is fixed for both builds. This
does not change or certify the CLI's default script deadline.

There are three independent untraced batches per case/build. Case order rotates
and debug/release order alternates. Each fresh benchmark process executes twice:

1. **Cold process:** compile first, then time native execution into a fresh store.
   Includes native addon loading, host startup, schema initialization, execution,
   settlement, and the executor's result handling. Compiler time is separate.
2. **Warm process:** execute into another fresh store in that same process.
   The addon and process are warm. The script host and store are still new.

“Cold” does not mean a cold OS page cache or a rebooted machine. These are
one-shot embeddings, not a long-lived activated runtime's pooled-host steady
state, installed-package CLI startup, or webhook admission measurements.

Traces and memory sampling are separate experiments, excluded from baseline
latency samples. CPU deltas cover the benchmark process, including its native
threads, **not** the separate Bun host/workers. They cannot be presented as
whole-system CPU use.

## Diagnostic findings

### Tiny scripts are cheap; starting and supervising them has a cost

For two release executions of `sequential-32`, 64 worker script evaluations took
44.63 ms in total, and compiling those scripts took 25.30 ms. Native request
decoding took 2.56 ms across two calls; TypeScript request serialization took
6.47 ms. These observations do not support blaming JavaScript arithmetic or
the N-API JSON boundary for several seconds of execution time.

The two host startups, however, took 1,935.92 ms inclusively. Each one-shot run
starts one host and isolates attempts in workers; it does **not** start a new
host for every ordinary step. That startup cost matters disproportionately for
tiny workflows and should not be extrapolated to an already activated runtime
that explicitly shares hosts.

History work also grows substantially in the scaling fixtures. Across two
release runs, sequential-8 recorded 350 full-fold calls and 2,670 input-event
visits; sequential-32 recorded 3,590 calls and 85,710 visits. The scripts grew
fourfold, but repeated history work grew much more. This is a concrete
optimization lead, not a proof of a particular complexity class.

### Durable work is not equivalent to evaluating a tiny script

In the combined release trace, two successful executions each ended with 83
events. Across those two invocations the profiler recorded:

| Span | Calls | Inclusive total |
| --- | ---: | ---: |
| `sqlite.append_events` | 124 | 4,548.83 ms |
| `sqlite.append_event_batch` | 20 | 724.04 ms |
| `runtime.fold_events` | 2,512 | 2,439.66 ms |
| `sqlite.project_run` | 506 | 1,418.83 ms |
| `sqlite.open_initialize` | 12 | 644.70 ms |
| `host.spawn_process` | 2 | 1,615.44 ms |
| `worker.compile_script` | 28 | 10.78 ms |

These are **overlapping inclusive intervals**, not mutually exclusive slices.
Do not sum them into a wall-time total. `append_events` includes history loading,
validation, index work, and transaction commit; it is not a measurement of disk
flush alone. Host read/execute spans include waiting for other work. Worker
“execute user code” includes awaiting managed-service RPCs, not just JavaScript
CPU instructions.

The fold counters report 63,150 input-event visits across those repeated folds,
not 63,150 newly stored events. The projection cache reports 450 hits and 56
misses: caching exists and is useful, but does not eliminate every other history
validation/fold path. Scheduling can change call counts between executions even
when final results and event counts match.

Source inspection explains why these are sensible investigation targets:

- [`durable/events/commits.rs`](../core/woml-engine/src/durable/events/commits.rs)
  owns transactional event append, full-history validation, index maintenance,
  commit, and post-commit cache publication.
- [`engine/history.rs`](../core/woml-engine/src/engine/history.rs) validates the
  complete history and folds prefixes for decisions, saga ordering, and other
  feature transitions.
- [`durable/events/cache.rs`](../core/woml-engine/src/durable/events/cache.rs)
  checks cache freshness against both sequence/count and event identity, and
  validates/rebuilds on misses.
- [`durable/opening.rs`](../core/woml-engine/src/durable/opening.rs) distinguishes
  full initialization/validation from the narrower prepared-store opener.
- [`host.rs`](../core/woml-engine/src/host.rs) owns host startup and shutdown;
  [`script_host_pool.rs`](../core/woml-engine/src/runtime/script_host_pool.rs)
  provides explicitly shared pooling where enabled. The direct one-shot calls
  measured here do not enable a cross-run host pool.

This supports investigating repeated validation and initialization. It does
**not** authorize skipping them: they protect crash recovery, exact operation
identity, authorization, and the rule that speculative state cannot escape a
failed transaction.

### Tracing is diagnostic, not free

All trace records are validated against the existing
[Performance Span v1 schema](schemas/performance-span.v1.schema.json).
Inclusive groupings preserve process labels; monotonic offsets are not compared
across processes. A process label is not a unique OS PID.

Native profiling synchronously serializes and appends records, and nested
profiling can add overhead inside outer spans. Therefore traced timings are not
substituted for untraced measurements, and the current data is not a CPU
flamegraph or a proof of exclusive function costs.

For example, the combined release trace observed 5,606 / 5,917 ms, versus
untraced cold/warm medians of 4,409 / 4,412 ms. The trace is a single independent
pair on a busy laptop, not a controlled estimate of a universal tracing-overhead
percentage.

Then, from `woml-cli/`:


Optional `--debug` and `--release` accept explicit native library paths. On each
run, the runner copies inputs into a new ignored directory beneath
`woml-cli/.woml/performance/`, retaining manifests, individual child results,

another **new** directory; existing directories are never overwritten. Native

## Follow-up investigation: reducing repeated history work

Status: source investigation and cost model completed. This section records the
proposal before implementation; see the implementation record below for actual
changes and verification. The following counts are not timing measurements.

### The precise repetition

There are three different kinds of repetition, with different risks:

1. **Inside one validator call.**
   `validate_event_history_against_definition` first folds the whole history to
   reject structural corruption. It then visits events in order, rebuilding
   `events[..index]` at 15 exclusive-prefix call sites and `events[..=index]`
   for legacy `run_succeeded`. These projections prove what was allowed **at
   that earlier moment**, not what is allowed in the final state.
2. **Across callers.** The append and atomic-batch paths validate the resulting
   candidate history before commit. Cache-miss projection reads also validate
   the complete history, then construct another fold state. Scheduler lease
   admission similarly validates and folds again. Those are separate places
   where returning an already validated state could eventually avoid work.
3. **Across connections and transactions.** Current projection caches are
   connection-local, with sequence/count and last-event identity freshness
   checks. Tentative append work removes the cached candidate; a successful
   commit publishes the replacement. Reusing these caches more broadly would
   need a separate authority and invalidation design.

The recommended first change targets **only item 1**. A cache hit for the
latest projection cannot substitute for an earlier prefix: later outputs or
decisions must not retroactively authorize a step that started too early.

### Quantifying a single final validation

The read-only analyzer
[`analyze-history-replay.ts`](../woml-cli/scripts/analyze-history-replay.ts)
opened all 120 recorded run histories with read-only SQLite connections. It
counts the fold requests made by the reviewed validator's match arms on these
already-successful histories. It is **not another workflow validator** and
does not certify whether arbitrary supplied events are valid.

The model is pinned to the reviewed `engine/history.rs` SHA-256:
`ea0b7221964cebf4fd0be40ba9e506f93868304ba5e4c12cddcbf31a231c5536`.
The standalone analyzer reads the baseline validator from the measurement's
recorded Git commit and verifies that fingerprint. It refuses mismatching
baseline source and candidate comparison files. This keeps historical analysis
reproducible after the engine changes; it is not a CI prohibition on edits.

All 12 histories per case yielded the same work counts despite different run
identities and permissible concurrent ordering:

| Case | History events | Current full-fold calls | Current event visits | Proposed event visits |
| --- | ---: | ---: | ---: | ---: |
| sequential-2 | 8 | 4 | 20 | 14 |
| sequential-8 | 20 | 10 | 110 | 38 |
| sequential-16 | 36 | 18 | 342 | 70 |
| sequential-32 | 68 | 34 | 1,190 | 134 |
| hooks-8 | 36 | 18 | 360 | 70 |
| state-8 | 44 | 10 | 242 | 86 |
| storage-4 | 24 | 6 | 84 | 46 |
| parallel-8 | 24 | 12 | 130 | 46 |
| foreach-8 | 42 | 4 | 122 | 82 |
| combined | 83 | 22 | 908 | 164 |

Each row models **one validation of the final history**, not the total work
performed throughout the run. Both current and proposed visits include the
unchanged initial full-history structural gate. The proposed column adds a
single local forward walk up to the last requested prefix. It is a count of
projection-transition applications, not elapsed time, SQL reads, or graph
readiness work.

For the specific sequential fixture with `n` successful script steps, the
history has `N = 2n + 4` events. Its prefix requests visit:

```text
2 + 4 + ... + 2n + (2n + 2) = (n + 1)(n + 2) events
```

Including the initial `N`-event gate gives `(n + 2)(n + 3)` current visits.
A monotone prefix cursor would instead require at most
`N + (N - 2) = 4n + 6` visits for this event shape. Thus the 32-step row models
1,190 versus 134 visits, about 8.9 times less folding work **inside that one
validation**. It does not predict an 8.9-times faster workflow.

### Recommended first implementation

Use a private, call-local prefix cursor backed by the existing
`ProjectionFoldState`, rather than a new projection algorithm or durable cache.

1. Retain the initial full-history `fold_events(events)` gate. This preserves
   structural corruption rejection and its precedence before definition checks.
2. Start a separate empty cursor after that gate succeeds.
3. At each existing exclusive-prefix read, advance the cursor to `index` and
   borrow its projection. At legacy `run_succeeded`, advance to `index + 1`.
4. Reuse that state for later requests in the same immutable event slice. Reject
   backward or out-of-range cursor requests defensively.
5. Discard the cursor when validation returns. Do not publish or reuse it across
   calls, connections, attempts, transactions, or workflow definitions.

The equivalence invariant is:

```text
cursor at k == ProjectionFoldState::from_events(events[..k])
```

It starts true at zero. Applying the identical existing transition to the next
event preserves it. The cursor must consume **every** intervening event,
including iteration-scoped events that skip the validator's ordinary match
arms. Otherwise later global checks would observe the wrong state.

Important edges that must stay unchanged:

- Exclusive versus inclusive prefix boundaries, especially legacy success.
- Both early `continue` paths: scoped events and non-parallel ordinary steps.
- Retry failure/schedule lookahead and atomic adjacency checks.
- Lifecycle adjacency, action ordering, and canonical identities.
- Event-time readiness and retry deadlines, not today's wall clock.
- Parallel concurrency/outcomes, fork settlement, wait resolution, and saga
  compensation/cleanup ordering.
- Structural validation of duplicate IDs, mixed runs/versions, bad sequences,
  events after terminal state, and malformed payloads before definition checks.

This does not reduce transaction count, change journal/sync settings, skip
authorization, remove recovery validation, or widen visibility. It stores one
working prefix, not all historical snapshots. Space still grows with the
projection's event identities, attempts, and context; it is not constant-memory
execution.

### Verification required before accepting the implementation

- Compare the cursor's projection with the legacy full replay at every prefix
  of historical and modern fixture histories, including scoped loop work.
- Differentially check accepted/rejected outcomes and errors for valid histories
  and mutations: deletion, duplication, reorder, identity/version drift, invalid
  start order, retry adjacency, forged hook order, early success, and bad saga
  ordering. Preserve a test-only replay oracle rather than relying on speed.
- Run the existing DAG, branch, parallel, retry, lifecycle, fork, iteration,
  wait, lock, and correction tests serially in bounded selections.
- Retain transaction tests such as
  [`invalid_second_payload_rolls_back_the_whole_batch_and_candidate_cache`](../core/woml-engine/src/durable/boundary_tests.rs),
  late-index failure rollback, failed recovery rollback, equal-count stale-cache
  rejection, and the
  [cross-connection append/projection test](../core/woml-engine/tests/durable_event_store.rs).
- Rebuild a candidate release library explicitly, retaining the existing
  baseline binary. Compare baseline release versus candidate release, not
  baseline debug versus candidate release. Use matching fixtures and more than
  one rotated batch, then trace separately.
- Check actual transition-visit counts as well as full-fold span counts. Merely
  making `runtime.fold_events` disappear from a trace does not prove work was
  eliminated. Add bounded diagnostic counters if necessary.

Only after those checks and measured benefit should later changes attempt to
return validated fold state to callers. Cross-call validation caching and store
opening changes remain separate proposals with broader invalidation risks.

## Implementation record: call-local prefix cursor

The approved implementation adds a private
[`HistoryPrefix`](../core/woml-engine/src/engine/history/prefix.rs) and replaces
the validator's 16 repeated prefix-fold sites with monotone cursor reads. All
existing definition, graph, identity, timing, and ordering predicates remain in
place, as does the initial complete structural fold. It uses the existing
`ProjectionFoldState::apply` transitions rather than copying their logic.

No durable store, cache publication, transaction, schema, migration, native
export, handler authorization, or workflow model is changed. The cursor is
bound to one immutable event slice, handles the inclusive legacy-success case,
and consumes iteration-scoped events even when their validation match arm was
skipped.

Opt-in profiling now records `runtime.history_prefix_cursor` with
`prefix_event_visits` and `prefix_requests`. Its **inclusive duration covers the
remaining definition-validation loop**, not exclusive fold CPU time. Transition
counts, together with the retained full-fold counts, allow the actual work to
be checked instead of just observing fewer `runtime.fold_events` spans.

The private [regression tests](../core/woml-engine/src/engine/history/tests.rs)
use the original full-prefix replay as a test-only reader. The predicates are
shared and unchanged; this is a differential projection/replay oracle, not an
independently reimplemented validator. They cover every prefix, repeated reads,
rejection/error precedence, deletion, duplication, reorder, mixed identities
and versions, early step execution, scoped loops, hooks, correction, and a
deterministic transition-count assertion.

Four successful modern histories were captured from the unmodified profiling
baseline, with their compiled definitions and exact event identities. Historical
fixtures are retained unchanged. Two projection-only historical examples omit
prerequisite steps; the tests explicitly preserve their structural acceptance
and their existing definition rejection. A separate complete retry history adds
the missing preparation attempt in test data so retry timing/adjacency is also
tested on a definition-valid example.

The timing comparison uses the existing runner with explicit release labels:

### Completion and correctness checks

The activated child uses the existing native manual-admission API. It binds
only an ephemeral loopback listener, prepares closed, activates explicitly, and
supplies no startup-trigger selection. It waits for the existing terminal
callback for the accepted run ID, including the race where the callback arrives
before the admission Promise resolves. It does not poll an inspector, execute
DAG nodes itself, or change scheduling/retry decisions.

After all timed runs and graceful runtime shutdown, read-only SQLite checks
verify contiguous event sequences, one successful business outcome with the
expected result, a finalized last event, no hidden operation/lifecycle/correction
failures, and distinct run IDs. One-shot results are additionally checked when
returned. There are no artificial sleeps, external services, secrets, remote
workers, or intentional failures in these workflows.

The runner saves raw results, databases, generated sources, resource readings,
trace files, and completion markers under ignored local experiment directories.
It requires at least 2 GiB available memory and disk before each child, limits
the matrix to serial execution, and places a three-minute watchdog around each
owned process group. A database or listener belonging to another project is
never touched. Compilation does not overlap measurements.

### Trace attribution

Existing spans are used without adding production instrumentation. Diagnostic
results retain whole-process inclusive span groups and native execution windows
for each run. The library's Rust/native span labels share one `Instant` origin;
fully contained native spans can therefore be grouped under the corresponding
`runtime.dispatch_run` or `runtime.execute_durable` window. Bun host/worker and
JavaScript offsets have different origins and are **not** assigned to those
windows by comparing timestamps.

A span within a run's time window is not proof of causal ownership: background
runtime maintenance may overlap. Spans crossing a window boundary are omitted
from that window but retained in the whole-process groups. Inclusive durations
overlap and must not be added into a wall-time pie. Untraced own-process CPU
still excludes Bun hosts/workers, and the callbacks and runtime-owner heartbeat
are part of the activated embedding's work.

## Proposed architecture and algorithm improvements

Status: **suggestions for future design and verification, not implemented by
this report**. The only runtime optimization already implemented in this
investigation is the call-local history-prefix cursor. Existing host pooling,
projection indexes, and immutable module caching predate these suggestions.
The goal is to reuse proven work without changing WOML's durable authority or
weakening isolation. None of the proposals has a promised speedup.

### 1. Separate runtime startup from request execution

**Purpose:** stop paying startup-oriented costs on ordinary requests when the
runtime can prove that the store has already been prepared.

Today, [`open`](../core/woml-engine/src/durable/opening.rs) performs full
initialization, while `open_ready` is deliberately narrower. Prepared admission
already uses the narrower path in places, but authority attachment, admitted-run
execution, and runtime-owner heartbeats still contain full-open paths. The
session traces above show full initialization during later activated runs.

The proposed design is an internal, owned **prepared-runtime context**. Startup
would establish the store's identity and compatibility, complete the required
migration/index/recovery work, and acquire runtime ownership. Request paths
could then open appropriately scoped connections through that context, retaining
per-operation authorization, transaction checks, and lease/fencing rules.
This does not require one global SQLite connection or a process-global cache.

In everyday terms: inspect the library building when opening it; do not repeat
that inspection for every borrowed book. Still check the borrower's permission
and record every loan.

Before implementation, specify how readiness becomes invalid after shutdown,
ownership loss, store replacement/restore, or incompatible external changes.
Keep a full startup path for one-shot and unprepared callers. Do not move global
crash recovery into live requests or assume that every index rebuild can simply
be deleted. A blanket replacement of `open` with `open_ready` is not the design.

**Verification:** compare fresh activation and repeated requests with identical
definitions, then test large retained stores, corrupt/future schemas, ownership
loss, cross-connection changes, restart, backup/restore, and index consistency.
Measure initialization calls and end-to-end latency separately. This is the
first priority because the repeated work has been directly observed.

### 2. Reuse validated execution state

**Purpose:** avoid reconstructing state that an immediate caller has just
validated, without treating a stale projection as durable truth.

The implemented [prefix cursor](../core/woml-engine/src/engine/history/prefix.rs)
only reuses work **inside one validation call**. The initial full structural
gate remains, and the cursor is discarded afterward. It is not a cross-call
cache, persistent checkpoint, or new append algorithm.

The next, narrower proposal is to let a validation operation return a private
validated-state object to immediate consumers that would otherwise fold the
same immutable history again. It must identify the exact definition, history,
and validation guarantees it carries. Structural validation and a cursor's
partial prefix must not be confused with a fully definition-validated final
projection; error precedence and historical prefix checks remain unchanged.

Only after that should a separate design consider incremental reuse across
appends. Conceptually:

```text
Validated state for an exact committed history
  + validated new event batch
  = tentative next state
  → commit events and required indexes
  → publish the next cached state only after commit succeeds
```

If a history is replayed from scratch after every single append, that replay
alone can visit `1 + 2 + ... + n = n(n+1)/2` events. Applying each new event
once can reduce that particular work toward `n` event applications. This is
not a claim that validation transitions have constant cost or that the entire
runtime becomes linear-time: graph queries, context growth, persistence, and
other checks still contribute.

**Safety and verification:** start with within-call reuse and differential
tests against full replay. Cross-call reuse needs a separate freshness design
covering store identity, definition identity, exact history revision/content,
and mutation visibility; equal event counts alone are insufficient. Preserve
transaction rollback, cross-connection refresh, corruption detection, and
commit-before-cache publication. Add fault-injection, restart, and stale-cache
tests before making any broader cache authoritative. Persisted checkpoints, if
ever proposed, require their own versioned compatibility design.

### 3. Make scheduling queries more incremental

**Purpose:** reduce repeated graph discovery when only a small part of a large
workflow changed. This is a source-based opportunity, not yet a measured
dominant bottleneck in our small graph samples.

[`ready_node_ids_for_projection_at`](../core/woml-engine/src/engine/readiness.rs)
currently reconstructs active nodes and an incoming-edge map, then filters the
graph's nodes. Some traversals repeatedly scan edges, and
[`CompiledWorkflowDefinition::node`](../core/woml-engine/src/model/queries.rs)
uses a linear search. This does not mean WOML has no indexes: readiness already
has a call-local edge map, and projection folding has event/attempt indexes.

A staged proposal is to prepare immutable node-ID and adjacency indexes once
per exact compiled definition. Dynamic eligibility would still be evaluated
against the current projection. If profiling justifies it, a later step could
track affected nodes and update a ready set or dependency counters rather than
reconsidering the entire graph after every transition.

This is like updating the few tasks affected by a delivery instead of rereading
the whole project checklist. But an ordinary predecessor counter is not enough:
branches change active edges, retries become eligible as time advances even
without a new event, and approvals, loops, forks, locks, correction, and workflow
settlement have distinct completion rules.

**Safety and verification:** preserve graph-source ordering, scoped result
visibility, concurrency limits, failure/cancellation behavior, and clock/deadline
wakeups. Rebuild derived scheduling state from the exact definition and accepted
projection after restart; a ready queue must not become a second workflow
authority. Differentially compare ready sets **and their order** against the
current implementation across event histories and clock advances. Benchmark
larger graphs before accepting extra cache complexity or claiming a gain.

### 4. Reduce per-invocation setup without weakening isolation

**Purpose:** investigate script preparation that could be reused without sharing
one invocation's mutable environment with another.

The existing [outer host pool](../core/woml-engine/src/runtime/script_host_pool.rs)
already reuses Bun processes. The [script host](../woml-cli/src/script-host/host.ts)
also maintains a bounded, digest-keyed immutable module/source-map cache. Those
features should be measured and preserved, not proposed as missing features.
Each invocation still gets a new worker; the
[worker execution path](../woml-cli/src/script-host/worker.ts) loads modules and
constructs an inline `AsyncFunction` for the request.

First measure worker bootstrap, module loading, compilation, user-code time,
and managed-service waits separately. Our tiny constant-result scripts did not
establish compilation as the main cost. Candidates include bounded reuse of
immutable preparation/artifacts where the existing Bun APIs and integrity
contracts actually support it. A host-side cache does not automatically make a
compiled function transferable into a fresh worker; verify feasibility first.

Worker pooling is **not** assumed safe and is not the first recommendation.
Current workers install invocation-specific global service, fetch, and console
facades, including non-configurable globals. Module mutable state, secrets and
redaction, materialized paths, operation identities, pending acknowledgements,
timers, and in-flight effects must not survive into another invocation. Merely
replacing the `context` object would not reset those boundaries.

**Verification:** preserve one-attempt authority, bounded caches and memory,
module integrity, deadline enforcement, cancellation/crash cleanup, secret
isolation, and fresh context. Any worker-lifetime redesign needs an explicit
reset/isolation proof and adversarial cross-invocation tests, plus comparative
measurements. If a safe reuse mechanism is unavailable or the cost is small,
retain the current isolated-worker design.

### Proposed order and acceptance criteria

1. Design the owned prepared-store request path and test its failure boundaries.
2. Investigate returning validated state to immediate callers; do not silently
   extend this into a persistent or cross-call cache.
3. Rerun the same matched-release, fresh-store/shared-store/activated baseline
   and separate diagnostics. Include retained-store growth and concurrent load
   where relevant, preserving slower samples and existing budgets.
4. Pursue incremental scheduling or invocation preparation only if attribution
   shows that the expected benefit warrants the additional complexity.

Each proposal should be a separately reviewable change with an explicit
correctness argument and reproducible before/after evidence. Keep durable
commit boundaries around external effects, authority checks, ambiguity rules,
and historical contract compatibility. None is authorization to weaken
durability, pool workers without proof, raise budgets, or claim the cold-storage
concern resolved.

## Further steps, not implemented here

1. Establish an installed-package/real-deployment baseline. The long-lived
   source embedding has now been measured, but not concurrent production load
   or network webhook round trips.
2. Design and test a prepared-store request path at the proven owned-runtime
   boundary. Quantify retained-store growth separately before removing any
   initialization, index rebuild, or recovery obligation.
3. Consider returning already-validated fold state to immediate callers only
   as a separately tested change. Cross-call caches require a separate freshness,
   corruption, rollback, restart, and cross-connection invalidation design.
4. Keep the cold-storage concern open. The new session controls and traces
   explain host reuse but do not prove the original cold regression fixed or
   identify an exclusive storage cause. Preserve slower samples and budgets.
5. If finer attribution is needed, use a bounded native sampling profile and
   correlate it with these spans. Distinguish CPU work, lock/IPC waits, and disk
   activity before choosing an optimization.

Larger history and graph sizes make repeated work more visible, but the scaling
cases also grow context and model size. A handful of points is not proof of a
particular asymptotic complexity. No overall “no regressions” or leak-free claim
can be made from these performance experiments alone.
