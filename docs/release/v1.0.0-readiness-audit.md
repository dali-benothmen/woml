# WOML v1.0.0 Release-Readiness Audit

Status: V1R0 and V1R1 complete on 2026-08-17. This document is the release ledger for
V1R2 through V1R9. It records the current evidence, frozen release contracts,
cleanup dispositions, verification baseline, and blocking work. It does not
authorize npm publication.

## 1. Executive Assessment

WOML has a complete product architecture and a viable cross-platform packaging
shape, but the repository is not yet ready to publish as v1.0.0.

The strongest release-ready boundaries are:

- the TypeScript/Bun frontend is the only WOML parser and compiler;
- `core/woml-engine` is the durable workflow authority;
- `core/woml-native` is the isolated N-API adapter and depends locally only on
  `woml-engine`;
- the retired JavaScript-chaining SDK and combined legacy Rust core are absent;
- the platform-neutral package staging path excludes native binaries;
- eight native target packages are mapped and contract-tested; and
- the CLI already exposes the complete authoring, execution, operational, and
  diagnostic command surface expected from WOML v1.

The release blockers are primarily productization work:

- package and repository identities still disagree;
- package/crate versions remain `0.1.x`;
- the monolithic CLI and Rust release gates are too resource-heavy and do not
  currently produce a reliable complete result;
- documentation still advertises `woml-cli`, v0.1, and stale Docker behavior;
- the release workflow publishes automatically for any `v*` tag and uses a
  repository token instead of an explicit protected publication gate; and
- completed implementation plans dominate the repository root.

None of these findings requires a new workflow engine or a second compiler.
They are addressed by the cleanup, documentation, build, and release phases in
the [professional release plan](../../WOML%20v1.0.0%20Professional%20Release%20Implementation%20Plan.md).

## 3. Frozen v1.0.0 Release Contracts

### 3.1 One public user package

The package installed by users is:

```text
woml@1.0.0
```

It owns this executable:

```text
woml -> dist/cli.js
```

Both supported installation commands install the same package and command:

```bash
bun add --global woml
npm install --global woml
```

Bun remains a runtime prerequisite even when npm performs the installation.
The package engine field must state the reviewed minimum Bun version.

### 3.2 Private compiler boundary

The current private package at [`woml/package.json`](../../woml/package.json)
becomes `@woml/compiler`. It remains `private: true`, is bundled into the CLI,
and is not separately published in v1.0.0.

TypeScript/Bun remains the single compiler implementation. Rust does not parse
WOML/XML in v1.0.0.

### 3.3 Native package boundary

The public `woml` archive contains no `.node` file. It declares exact-version
optional dependencies on the native package family:

| Runtime | Package | Binary |
| --- | --- | --- |
| macOS x64 | `@woml/cli-darwin-x64` | `woml-core.darwin-x64.node` |
| macOS ARM64 | `@woml/cli-darwin-arm64` | `woml-core.darwin-arm64.node` |
| Windows x64 | `@woml/cli-win32-x64-msvc` | `woml-core.win32-x64-msvc.node` |
| Windows ARM64 | `@woml/cli-win32-arm64-msvc` | `woml-core.win32-arm64-msvc.node` |
| Linux x64 glibc | `@woml/cli-linux-x64-gnu` | `woml-core.linux-x64-gnu.node` |
| Linux x64 musl | `@woml/cli-linux-x64-musl` | `woml-core.linux-x64-musl.node` |

[`woml-cli/scripts/native-release.ts`](../../woml-cli/scripts/native-release.ts).
Users never choose a native package manually.

### 3.4 Version contract

The intended release identity is v1.0.0. The release workflow must reject a tag
or requested version that differs from the collected package family.

Release versions that must be reviewed and aligned include:

- public `woml` package;
- private `@woml/compiler` package metadata;
- generated `@woml/cli-*` packages;
- `woml-native` crate;
- `woml-engine` crate when version metadata is exposed in build artifacts; and
- the VS Code extension's independently reviewed v1 release.

Protocol, event, model, store, definition-package, and schema versions are not
product release numbers. They remain independently versioned.

### 3.5 Repository and publication contract

The intended source repository is `dali-benothmen/woml`. The owner performs the
actual GitHub rename. Source metadata and links are updated only to the real
repository identity.

Build and release-candidate automation must be safe to run without publishing.
Publishing is allowed only in V1R9 through an explicit, protected invocation
performed with the product owner. A normal push, pull request, or tag push must
not accidentally publish packages.

The current preferred publication identity is npm trusted publishing from the
exact GitHub workflow, protected by an `npm-production` GitHub environment.
The final registry setup is rechecked against current npm requirements in V1R9.

### 3.6 Source-history contract

These items are compatibility history and must not be renamed mechanically:

- schema `$id` values, including historical `https://cronflow.dev/...` IDs;
- `$ref` and `x-previousVersion` links that point to those IDs;
- historical model, event, store, package, protocol, and inspection versions;
- migration fixtures that prove old durable data remains readable; and
- explicitly documented compatibility paths.

Live product names, install commands, package names, repository links, test
names, and phase labels are release residue and may be changed.

## 4. Current Architecture and Dependency Boundary

```text
.woml source
  -> woml/src/parser.ts
  -> woml/src/compiler.ts
  -> versioned compiled DAG / definition package
  -> woml-cli/src/cli.ts
  -> woml-cli/src/rust-executor.ts
  -> core/woml-native/src/bridge.rs
  -> core/woml-engine
  -> SQLite event history and folded projections
  -> isolated Bun script/provider hosts when JavaScript is required
```

### 4.1 Frontend

[`woml`](../../woml) owns parsing, source locations, grammar validation,
references, module resolution, reusable definitions, capability analysis, and
compiled-model lowering. Its current compiled workflow schema generation
reaches Model v15 and Definition Package v10.

### 4.2 CLI and Bun hosts

[`woml-cli`](../../woml-cli) owns the public command, configuration, secret
resolution, native loading, trigger/provider transports, terminal rendering,
background hosting, and isolated script/provider workers.

The current script-host protocol is v8. Older schemas remain present for
compatibility tests.

### 4.3 Rust authority

[`core/woml-engine`](../../core/woml-engine) owns execution, event persistence,
folding, recovery, retries, idempotency, approvals, triggers, control flow,
workflow calls, lifecycle, runtime policies, durable state, services,
observability, backup, retention, and presentation projection.

[`core/woml-native`](../../core/woml-native) is the only N-API crate. The
architecture gate proves that its only local dependency is `woml-engine` and
that it does not import the removed legacy graph.

### 4.4 Persistence

WOML runtime state defaults under `.woml/` and uses the active SQLite durable
store. Runtime databases and backup archives are not package content or Git
source. The old mutable Cronflow runtime is not part of the current dependency
graph.

### 10.2 Frontend baseline finding

Command:

```bash
cd woml-cli
bun test ../woml/tests
```

Result:

```text

1 failed
261 total across 25 files
```

The failing case is in `woml/tests/notifications.test.ts`. It expects
`WOML_NOTIFY_UNSUPPORTED_PROVIDER`, while the current provider-specific
validation returns `WOML_DISCORD_ATTRIBUTE_REQUIRED`. The implementation and

### 10.3 CLI baseline finding

Command:

```bash
cd woml-cli
bun test tests
```

The suite did not produce an authoritative final result. Observed failures were:

- loopback listener creation rejected by this sandbox in Slack, production,
  and services-composition journeys;
- an embedded `bun run build` exceeded a five-second test hook and was
  terminated;
- another listener-dependent test waited 20 seconds for readiness after the
  bind failure; and
- Bun 1.3.14 ended the process with a segmentation fault after approximately
  108 seconds.

This result does not prove a runtime defect, because local binding is forbidden
in the audit sandbox and the process itself crashed. It does prove the complete
CLI suite is not currently a reliable single release gate: tests rebuild inside
tests, rely on implicit local networking, have short hook timeouts, and provide
no final categorized summary after a runner crash.

### 10.4 Full Rust workspace finding

The complete workspace was attempted twice with one job:

```bash
cargo test -j 1 --locked --release --manifest-path core/Cargo.toml --workspace

cargo test --config profile.dev.debug=0 \
  --config profile.dev.incremental=false \
  -j 1 --locked --manifest-path core/Cargo.toml --workspace
```

Both attempts spent several minutes compiling/linking 75 separate integration
test binaries without reaching test execution and were stopped to protect the
development machine. The targeted engine-library and architecture suites pass.

The release gate needs two levels:

1. a fast, named, deterministic baseline for ordinary changes; and
2. the complete integration matrix in CI with explicit sharding, timeouts, and
   artifact reuse.

The release profile should not apply size-optimized LTO to every test binary.

## 12. Documentation Audit

### 12.1 Current strengths

- Architecture, production runtime, triggers, services, recovery, backup,
  retention, modules, workflow calls, providers, and terminal behavior already
  have substantial documentation.
- Versioned schemas and protocol explanations provide strong implementation and
  compatibility evidence.

  user and maintainer docs.

- documentation is broad but lacks one v1 getting-started path and one complete

- the publish workflow creates a GitHub release in the same unreviewed path;
- package artifacts do not yet carry approved v1.0.0 identities; and
- clean registry installation is not performed after publication.
